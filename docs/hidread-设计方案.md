# hidread 设计方案

> 精简版。协议字节级推导、实测数据与源码索引见 [`hidread-设计方案-详细版.md`](./hidread-设计方案-详细版.md)。

## 一句话

一个 800 KB 的单文件 Windows 托盘程序：定时读取 ATK 方案鼠标的电量，把每一次「设备在线」记成一条会话，按天落盘，本地网页查看曲线与使用时段。

## 它解决什么问题

鼠标电量和续航是黑的：驱动只告诉你「还剩 70%」，不告诉你「这 70% 撑了多久、什么时候掉的、每天用多少小时」。

hidread 做三件事：

- **按节拍采样**，记录电量与有线状态，形成可回看的曲线；
- **识别使用时段**，把「设备在线」切成会话，累计成每日时长与周视图；
- **推导充放电周期**，从满充到耗尽算一次续航，供选型参考。

它不追求「精确到秒的行为分析」，只求长期趋势可信、数据可自己复算。

## 数据从哪来

设备是 ATK 方案的 2.4G 鼠标（`VID 373B`，PID `11D9`/`11E7`），走标准 HID 接口（usage page `FF02`）。

读取方式是「发一帧输出报告，再读一帧输入报告」：输出报告是固定 16 字节的请求帧，输入报告返回电量百分比、是否插线、充电状态。校验和算法、字段偏移、必须照抄的读法都在详细版里——**任何「优化」读取顺序的尝试都会导致设备不应答**。

关键约束：同一句柄上的并发阻塞读会与写/IOCTL 互锁，所以**只有节拍线程持有设备句柄**，HTTP 线程永远不碰设备。

## 时间怎么算

这是全项目最容易出错的部分，也是迭代最多的地方。

**业务日**：每天从 04:00 算到次日 03:59。凌晨的使用属于前一天，这样「熬夜到 1 点」不会把时间轴撑成 0 点起，也不会让两个页面差一天。

**会话**：一次连续在线算一段。

- 开始 = 首次读到数据的时刻。若这是从离线恢复，再前移半拍（真实上线发生在两次采样之间），但不早于上次判离线的时刻。
- 结束 = 末次成功读取 + 半拍。半拍取**上一次实际间隔的一半**，而不是配置里的标称节拍。
- 依据：事件落在两次采样之间的位置不可知，取中点是无偏估计——有时多记、有时少记，长期抵平。

**判离线**：静默时长 ≥ `max(2 × 快探, 30 秒)`，且失败次数达到配置值。

- 快探 = `休眠档位 / 3`，夹在 10 秒与节拍之间。平时按节拍慢采，一旦读不到就提速确认，避免判定延迟被节拍拖长。
- 阈值里**不再叠加休眠档位**：末次读取本身已在休眠时刻附近（休眠前设备一直上报），再叠加等于算两遍。

**相位抖动**：每次采样间隔加 ±10% 随机抖动。节拍与休眠档位若成整数比（默认都是 60 秒），采样点会与休眠周期锁死在同一相位，误差永远偏向一侧；抖动让相位缓慢漂移。抖动对称，期望不变，配合「半拍用实际间隔」，两端都无系统偏差。

**图与账分离**：周视图的色块按合并区间绘制（视觉连续），时长统计用未合并的原始会话（休眠间隙不计入）。图负责好看，数字负责准确。

## 数据怎么存

全部是按天 CSV，没有数据库（理由见详细版附录 D）。

| 文件 | 内容 | 写入时机 |
|---|---|---|
| `sessions.csv` | 每次会话一行：起止时间、时长、结束原因 | 会话结束 |
| `history-YYYY-MM-DD.csv` | 采样点：电量、有线、链路、读取耗时 | 值变化或基线间隔 |
| `cycles.csv` | 充放电周期：满充→耗尽 | 周期闭合 |
| `events-YYYY-MM-DD.csv` | 状态跳变：上线、离线、重启 | 状态改变 |
| `config.json` | 配置；未知键忽略，缺项走默认 | 保存设置 |

清理按**目录总量**（默认 200 MB），超限从最旧的按天文件删起，最近 7 天硬保留，累积文件（sessions/cycles）不参与。

## 接口

| 路径 | 作用 |
|---|---|
| `/` | 设置页（内嵌 HTML，无外部资源） |
| `/battery` | 当前电量快照与链路状态 |
| `/history?hours=&max=` | 曲线数据，极值在降采样前计算 |
| `/daily?days=` | 每日在线时长与电量跨度 |
| `/week?days=&start=` | 周视图：按业务日切分的会话段 + 活跃时间轴 |
| `/api/config` | 读写配置（POST 需 `application/json` + 回环来源） |
| `/health` | 存活与设备状态 |

写接口只接受同源请求：Origin 解析出 host 后精确比对（覆盖整个 `127.0.0.0/8` 与 `::1`），不接受 `text/plain`——避免本机恶意页面改配置。

## 配置

| 项 | 默认 | 说明 |
|---|---|---|
| `tick_s` | 60 | 采样节拍，实际间隔带 ±10% 抖动 |
| `sleep_s` | 60 | 驱动里的休眠档位，决定快探间隔 |
| `offline_after_fails` | 2 | 判离线前至少确认几次（2–10） |
| `history_interval_s` | 300 | 稳态写盘间隔 |
| `data_max_mb` | 200 | 数据目录上限 |
| `cycle_*` | — | 满充阈值、最短充电、终止电量、周期超时 |
| `pids` | `["11D9","11E7"]` | 兼容的 PID 列表 |

配置在 exe 同级的 `config.json`，数据在 `data/`。整个目录可整体搬走。

## 目录与发布

```
hidread.exe          单文件，无运行时依赖
config.json          可选，缺省用内置默认值
data/                历史数据（不可删）
plugins/             LiteMonitor 插件（可选）
使用说明.txt
```

发布流程：`cargo test` → `cargo build --release` → 把 exe 与说明、示例配置、插件打进 `dist/hidread-<版本>/` → 压缩并记录 SHA256。

**升级只需替换 exe**：配置与数据都在同级目录，新版对旧配置的未知键宽容、缺项走默认。只有发布说明明确写「需要迁移」时，才需要动数据。

## 已知取舍

- **鼠标休眠 ≠ 人离开**：程序只能看到设备是否上报，无法知道你是否在敲键盘。1 分钟休眠的驱动意味着「静止 1 分钟」不会被判为离开——这是有意的，代价是「离开后的 1 分钟」仍算使用。
- **精度绑定节拍**：两端各用半拍近似，节拍越小越准。想更快判定就调小节拍，代价是采样更频繁。
- **不支持同时跟多个同款鼠标**：同一时刻只维护一个设备会话。
- **HTTP 单机**：默认只监听回环；改成 `0.0.0.0` 后写接口仍只接受回环来源，GET 会对局域网开放（只读数据）。
- **时钟回拨**：会话区间用半拍下限保护，避免时间线倒流重叠。

## 展望：从一只鼠标到一个外设面板

现在的代码把「设备」写死成了「ATK 鼠标」：VID/PID 是常量，解析器是一个固定函数，历史文件不分设备。如果想监测更多外设——比如蓝牙连接的 BS3 Pro 散热器、键盘、耳机——需要三步演进。

**第一步：把设备变成数据，而不是代码**

引入一张设备描述表：`vid`、`pid`、`usage_page`、报告长度、字段偏移、校验算法、能力位（电量 / 温度 / 风扇转速）。解析器抽象成 trait，每个设备一个实现，枚举时按描述表匹配。

收益不止于多设备：现在协议细节散在 `hid.rs` 与详细版文档两处，收进描述表后，「支持新设备」从改代码变成加一行配置。

**第二步：历史按设备分家**

`sessions.csv` 与会话上限都假设「只有一只鼠标」。多设备后需要 `device_id` 维度：`sessions-<device>.csv`，或加一列并在查询时过滤。周期统计同理——充电周期是「某设备」的属性，不能混算。

**第三步：界面从单卡片变成设备列表**

设置页现在是三段固定面板。多设备后需要设备选择器或并排卡片，每个设备独立曲线与时段。数据模型先行，UI 只要按 `device_id` 分组即可复用现有绘制逻辑。

**蓝牙设备的现实约束**

BS3 Pro 这类散热器有两种可能：

- 如果它暴露 **HID over GATT（HOGP）**，Windows 会把它枚举成 HID 设备，现有 `hidapi`/SetupAPI 路径可以直接打开，但**电量未必在标准报告里**——需要按厂商自定义报告解析，仍要先抓到报文。
- 如果它只提供 **BLE GATT 服务**（自定义 Service/Characteristic），就不在 HID 体系内，需要走 WinRT 的 `BluetoothLEDevice` + GATT 读写，是另一条技术栈；好处是不受 HID 句柄独占限制，坏处是要处理配对、断连重连与异步 API。

判断方法很简单：连上设备后跑一次 `Get-PnpDevice`，看它是否出现在 HID 类下；或用 `tools/my_devices.py` 枚举一遍，能列出接口的就是 HID 路径。

**不建议现在动的部分**

节拍引擎、会话模型、存储格式这三块，即使扩展到十种设备也不需要重写——它们只依赖「某个设备在某个时刻是否在线、电量多少」，与设备类型解耦。真正要改的是「设备身份」这一层。这也是当前架构最值得保留的地方：把不确定性关在采集层，上层的账本保持简单。
